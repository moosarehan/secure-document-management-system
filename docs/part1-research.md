# Part 1 — Security research and design

The prototype protects confidential documents against database-only disclosure and enforces the current document policy at the application boundary. The application server and its operating account are trusted to handle plaintext and keys. A live server compromise can therefore expose documents and bypass policy. A database writer can also change authorization state or cause service loss. Cryptographic checks specifically cover document content, selected document metadata, and audit history.

## 1. Data storage and confidentiality

- **Alternatives.** Plaintext files protected by OS permissions are simple but expose contents when files or backups leak. Full-disk encryption helps against a stolen offline drive but a running host or database export can still expose plaintext. An encrypted filesystem or object store reduces database load but introduces a second lifecycle for uploads, deletes and backups.
- **Selected approach.** Store metadata, accounts, grants, sessions and audit records in SQLite. Put encrypted document payloads, wrapped keys and nonces in a dedicated table in that database. A single transaction can commit or roll back metadata, ciphertext and the matching audit event together. Keep the key file separate from the database and back it up under separate access controls. [SQLite transaction documentation](https://www.sqlite.org/lang_transaction.html)
- **Protection boundary.** The application accepts up to 5 MiB per upload, parses file parts into memory, and encrypts the document before issuing any persistent write. HTTPS is the intended transport outside the local demonstration. Plaintext remains in browser and server memory during a transfer, and OS swapping or crash dumps may create copies outside application control.
- **Exposure.** A database-only copy reveals sanitized filenames, approximate document sizes, timestamps, accounts, password hashes, grants, and audit events. Ciphertext lengths expose plaintext lengths after subtracting the fixed authentication tag. Keys are required to decrypt the payloads. Database modification can still damage metadata, delete rows or change permissions. Encrypting selected metadata or using keyed indexes and size padding would reduce disclosure at the cost of query simplicity and storage.

## 2. Cryptographic protection

- **Alternatives.** A single symmetric data key is easy to operate but couples every document to the same data key. Unkeyed hashing can detect accidental changes, but a database writer can replace both payload and hash. Digital signatures can provide independent origin verification when a trusted verification key is available, but add identity and signing-key management. Public-key wrapping per recipient and browser-side encryption reduce the trust placed in the server but add enrollment, recovery and sharing complexity. AES-GCM and ChaCha20-Poly1305 both provide authenticated encryption with associated data.
- **Selected approach.** The server generates a fresh 256-bit data encryption key for each upload or replacement. AES-256-GCM encrypts the content. A separate server key encrypts the data key using AES-256-GCM. Each operation uses a fresh 96-bit nonce, and the wrap nonce has an active-row uniqueness constraint. Associated data binds payloads and wrapped keys to their purpose, document ID, owner ID and filename. The server verifies both tags for authorized retrieval and explicit integrity verification. A tag failure blocks plaintext release. The authentication tag establishes validity under the application key and can accept a complete older valid version if a database writer restores it. [PyCA authenticated encryption](https://cryptography.io/en/stable/hazmat/primitives/aead/) · [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)
- **Key lifecycle.** Initialization creates separate random keys for document wrapping, audit authentication and cookie signing. The application process loads them from the external key file. Rotating keys is a future controlled migration. Wrapping-key rotation would require rewrapping every data key and tracking key versions, and compromise may require re-encrypting data with new data keys since copied old ciphertext can remain decryptable. Audit key rotation requires preserving historical verification or exporting an authenticated checkpoint. Cookie key replacement invalidates old signatures. Key loss requires restoration from protected backups. Document keys cannot be recovered from ciphertext alone.
- **Credential compromise.** An operator can disable an account or reset its password, which removes its active sessions. The operator should also review access events and revoke affected grants as appropriate. Data previously retrieved under valid credentials may already have left the system.
- **Client/server split.** The client submits credentials and files, transmits its session cookie, and receives authorized downloads. The server handles password hashing, authorization, encryption, key unwraps and integrity checks. This avoids client-side key distribution, while making the server a high-value trust boundary. Random wrapping nonces have a collision probability that grows with uploads under a key, so a higher-volume design needs key usage limits and a rotation policy.

## 3. Authentication and authorization

- **Alternatives.** Global RBAC simplifies administration but cannot express individual document sharing by itself. Owner-managed discretionary access control supports per-document delegation. ABAC could add departmental, device or classification conditions, but increases policy and testing complexity. Self-contained signed sessions simplify storage but require revocation state for immediate invalidation.
- **Selected approach.** An operator provisions accounts. Password verification uses Werkzeug scrypt with independent salts. The server rate limits repeated login failures by peer address and responds generically to unknown names and bad credentials. A signed, HttpOnly, SameSite cookie carries an opaque session token. Only its hash is stored server-side, along with account binding and a fixed expiry. Every protected operation checks the server session and account state. POST requests use a session-bound CSRF token. HTTPS deployments retain Secure cookies. [Werkzeug password utilities](https://werkzeug.palletsprojects.com/en/stable/utils/#module-werkzeug.security) · [Flask web security](https://flask.palletsprojects.com/en/stable/web-security/)
- **Policy.** Every account may own documents. A viewer may list, inspect, verify and download an assigned document. An editor can also replace its content. Only the owner can grant or revoke access and delete the document. The administrative role adds audit visibility. Access to somebody else's documents still requires an explicit grant. Unknown or unshared IDs return the same 404 response. A user with visibility but insufficient privileges receives 403. Ownership and current grants are checked by the server independently of displayed controls.
- **Limitations.** Peer rate limits can inconvenience users sharing an address and have limited value against distributed attempts. MFA, external identity, organization-wide policies and recovery self-service are out of scope. A writer with direct database access can affect account and grant state. File permissions and separate service credentials are part of the trust assumptions.

## 4. Secure document sharing

- **Alternatives.** Public bearer URLs are convenient but holder access can survive forwarding or browser history disclosure. Short-lived bearer links reduce the window while still granting access to the holder. Client-side key distribution provides greater separation from the server, but a recipient can retain the key and encrypted download.
- **Selected approach.** The owner grants Viewer or Editor access to an existing account, optionally with an expiration. The recipient signs in and sees the document in the same list as their own files. An ordinary document URL conveys an identifier. Authorization reads the live ACL for every request. Expired or revoked grants stop authorizing new requests, and the owner can grant a different role without producing a new downloadable URL.
- **Download handling.** The application returns an attachment as generic binary with MIME sniffing and caching discouraged. Plaintext lives in memory during request processing. Downloaded copies live on recipient devices. Revocation takes effect for requests authorized after the revocation commits. A request already authorized may finish, and the system cannot recall files a recipient already downloaded or copied. Sensitive collaboration could instead rely on a managed viewer and endpoint controls, with continued limits on copying.

## 5. Auditing and accountability

- **Alternatives.** Plain audit rows are searchable but a database writer can silently edit or delete them. An unkeyed hash chain can be recomputed. External append-only storage and independently retained checkpoints can detect coordinated rollback but require a second protected service and reconciliation.
- **Selected approach.** Record account creation and management, sign-in outcomes, logout, document access and changes, sharing grants and revocations, authorization denials, integrity failures and audit viewing. Audit events use UTC timestamps, account IDs when known, document IDs and narrowly typed operation details. Passwords, cookies, keys and file contents are excluded. Each row is authenticated by HMAC-SHA-256 over the event and previous MAC. A separately authenticated head records the expected last sequence and MAC. Appends check the tail record and checkpoint. Audit review checks the full chain before presenting its latest records. [Python HMAC API](https://docs.python.org/3/library/hmac.html)
- **Investigation.** An administrator can correlate actor IDs, target IDs, operation outcomes and peer addresses from sign-in events. Repeated denied access, failed sign-ins or integrity failures merit review, and those patterns require context before assigning intent. Audit privileges confer no implicit document access.
- **Limitations.** A full database rollback can restore a consistent older chain and head. A compromised audit key can enable forgery, and deletion of the database can prevent investigation. The next step for these threats is remote retention with independent checkpoints and alerts. Audit review verifies the complete history, giving verification cost proportional to history size.
